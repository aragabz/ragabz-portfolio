## Executors: Where Tasks Actually Run

The executor determines how the scheduler hands work to a worker. This is the single biggest architectural decision.

| Executor | Scale | When to use |
|----------|-------|-------------|
| `LocalExecutor` | 1 machine, parallel tasks | Local dev (the default) and single-node production |
| `CeleryExecutor` | Many machines, queues | The classic multi-node choice |
| `KubernetesExecutor` | Per-task pods | Cloud-native, elastic scale |
| Multiple executors (e.g. `executor = CeleryExecutor,KubernetesExecutor`) | Hybrid | Route specific tasks to a different executor via the task's `executor` argument |

### LocalExecutor

Runs tasks in parallel processes on one machine. Fine up to a modest number of concurrent tasks, provided the box is sized correctly.

```ini
# airflow.cfg
[core]
executor = LocalExecutor
parallelism = 8
```

### CeleryExecutor

The workhorse for mid-size deployments. Tasks are pushed to a broker (Redis or RabbitMQ) and picked up by Celery workers, which you can scale horizontally:

```ini
[core]
executor = CeleryExecutor

[celery]
broker_url = redis://redis:6379/0
result_backend = db+postgresql://airflow:airflow@postgres/airflow
```

<Callout variant="note">
CeleryExecutor requires a **PostgreSQL** (or MySQL) metadata database — SQLite can't handle concurrent writes. This is Airflow's first hard production requirement.
</Callout>

### KubernetesExecutor

Every task gets its own pod. The scheduler creates pods on the fly, so capacity scales automatically with demand and you get strong isolation between tasks:

```ini
[core]
executor = KubernetesExecutor

[kubernetes_executor]
namespace = airflow
```

This is a popular choice for teams already on Kubernetes. You pay with higher overhead per task (pod startup time) and more moving parts.

## Connections and Variables: Never Hardcode Secrets

The number one production mistake is stuffing credentials into DAG code. Airflow gives you proper homes for configuration:

- **Connections** — credentials for external systems (databases, APIs, cloud providers), stored encrypted in the metadata DB or in a secrets backend
- **Variables** — simple key/value configuration for your DAGs

```python
from airflow.sdk import Connection, Variable

api_token = Variable.get("api_token", default="")
conn = Connection.get("my_database")
```

Retrieve them at runtime inside tasks — never commit secrets to git, never build them into DAG files.

### Use a secrets backend

For production, read connections and variables from a real secrets manager instead of storing them in the metadata DB:

```ini
[secrets]
backend = airflow.providers.amazon.aws.secrets.secrets_manager.SecretsManagerBackend
backend_kwargs = {"connections_prefix": "airflow/connections", "variables_prefix": "airflow/variables"}
```

The same pattern exists for GCP Secret Manager, Azure Key Vault, HashiCorp Vault, and others. Now rotating a credential is a single update in your secrets manager — no DAG redeploy, no metadata DB access.

<Callout variant="warning">
Configure a real auth manager for the API server/UI (`[core] auth_manager`, e.g. the FAB or Keycloak auth manager instead of the default Simple auth manager), never expose it to the public internet, and treat the metadata database as highly sensitive — it contains connection details.
</Callout>

## Configuration Knobs That Matter

A few settings have outsized impact on reliability:

```ini
[core]
# Max seconds to import a single DAG file — keep it low
dagbag_import_timeout = 30
max_active_runs_per_dag = 3

[scheduler]
# How often the scheduler heartbeats
scheduler_heartbeat_sec = 5

[dag_processor]
min_file_process_interval = 30
parsing_processes = 2

[celery]
worker_concurrency = 8
```

Tuning is iterative: watch the scheduler's metrics and adjust `parsing_processes` and `worker_concurrency` based on actual load. Airflow 3.x reworked scheduling around time-based `schedule` semantics and made the scheduler more efficient by default, so keep the image reasonably current.

## Testing DAGs in CI

Your pipelines deserve the same rigor as your application code. Airflow DAGs are Python — test them like Python.

### Assert the graph is correct

```python
# tests/test_dags.py
import pytest
from airflow.models import DagBag

def test_no_import_errors():
    dag_bag = DagBag(dag_folder="dags/", include_examples=False)
    assert not dag_bag.import_errors, (
        f"DAG import failures: {dag_bag.import_errors}"
    )

def test_dag_has_schedule():
    dag_bag = DagBag(dag_folder="dags/", include_examples=False)
    for dag_id, dag in dag_bag.dags.items():
        assert dag.schedule is not None, f"{dag_id} has no schedule"
```

### Test task logic in isolation

The `@task` functions wrap plain Python — unit test the underlying function directly:

```python
def test_transform():
    from my_project.tasks import transform
    # .function is the undecorated Python callable behind @task
    assert transform.function("  hello  ") == "hello"
```

Run these in CI on every pull request. A broken DAG caught in CI costs seconds; the same bug in production costs a morning.

<Callout variant="tip">
Keep the `airflow` package version in your test environment identical to production. DAGs written for Airflow 2.x can break subtly under 3.x — test against the same version your scheduler runs.
</Callout>

## Monitoring and Alerting

Airflow provides the primitives; you must wire up the alarm.

### Metrics with statsd / Prometheus

Airflow emits statsd metrics (or you can use the Prometheus exporter). Track at minimum:

- **Scheduler heartbeat** (`scheduler_heartbeat`) — if it stops, nothing runs
- **DAG parse time** — climbing parse times warn of DAG-bag bloat
- **Skipped/failed task instances** — rising failures signal flaky tasks or infrastructure
- **Queue depth** (Celery) — tasks queued but not executing = workers under-provisioned

### Deadline alerts and failure callbacks

```python
from datetime import timedelta

from airflow.providers.slack.notifications.slack_webhook import SlackWebhookNotifier
from airflow.sdk import AsyncCallback, DeadlineAlert, DeadlineReference, dag

@dag(
    schedule="@hourly",
    deadline=DeadlineAlert(
        reference=DeadlineReference.DAGRUN_QUEUED_AT,
        interval=timedelta(minutes=45),
        callback=AsyncCallback(
            SlackWebhookNotifier,
            kwargs={"text": "Deadline missed: {{ dag_run.dag_id }}. Check Airflow."},
        ),
    ),
)
def hourly_pipeline(): ...
```

Airflow 3 removed SLAs (`sla_miss_callback`); Deadline Alerts (experimental, 3.1+) replace them. For failures inside a task, use failure callbacks (`on_failure_callback` on tasks or the DAG) or a listener plugin (`on_dag_run_failed`) for a single central hook — wire one and route it to your alerting channel (Slack, PagerDuty, email).

### Structured logging

Ship task logs to remote storage or a log aggregator:

```ini
[logging]
remote_logging = True
remote_base_log_folder = s3://my-airflow-logs/
remote_log_conn_id = aws_default
```

Enable remote logging (S3/CloudWatch/GCS) so task logs survive worker restarts and are searchable.

## Deploying DAGs Safely

The right way to ship DAGs is via **CI/CD**, not manual copying:

1. Store DAGs in a git repository (ideally as a Docker image or synced volume).
2. In CI: lint, run the tests from above, and validate imports.
3. Build a Docker image containing the DAGs and **pinned** dependency versions.
4. Deploy the image to your Airflow cluster — the DAG processor picks up the new DAG definitions on its next parse.

A pinned image with reproducible dependencies turns "why did my DAG break?" into "here's the diff between these two images."

<Callout variant="warning">
DAG versioning matters. Since Airflow 3, each structural change to a DAG is recorded as a new DAG version and the UI shows which version each run used — but Airflow won't backfill or rewrite past runs for you. Communicate changes to whoever depends on the schedule before you deploy.
</Callout>

## A Production Checklist

Before you call your Airflow deployment production-ready:

- [ ] PostgreSQL metadata database, backed up regularly
- [ ] Executor chosen for your scale (`LocalExecutor` at minimum)
- [ ] Secrets backend configured; no credentials in DAGs or git
- [ ] UI/API server authentication configured, not publicly exposed
- [ ] Retries/timeouts/deadline alerts set on mission-critical tasks
- [ ] CI tests: no import errors, expected graph structure, unit-tested tasks
- [ ] Metrics, structured logging, and alerting wired up
- [ ] Pinned, reproducible deployment image
- [ ] Documented backfill and rollback procedure
