Avoidable recomposition is the most common performance bottleneck in Compose. Here’s how to spot and fix it.

<Callout variant="tip" title="What you'll learn">
- How to spot `remember` pitfalls and stale values
- When to use `SnapshotStateList` instead of a plain `MutableList` inside `mutableStateOf`
- Safe patterns for `LaunchedEffect` and `DisposableEffect`
</Callout>

### Common `remember` traps

```kotlin
@Composable
fun ItemSummary(items: List<String>) {
    // ❌ No keys: computed once on first composition, then stale
    // when the caller passes a different list.
    val staleCount = remember { items.size }

    // ✅ Key `remember` on its inputs so it recomputes when they change
    val itemCount = remember(items) { items.size }

    // ✅ For a list you mutate locally, use an observable snapshot list
    val selected = remember { mutableStateListOf<String>() }
}
```

`mutableStateListOf` creates a `SnapshotStateList`: reads are tracked by the snapshot system, so adding or removing items recomposes only the composables that actually read the list.

### `SnapshotStateList` vs. a plain list in `mutableStateOf`

| Operation | `mutableStateOf(mutableListOf())` | `SnapshotStateList` (`mutableStateListOf()`) |
|-----------|------------------------------|---------------------|
| `add/remove` | Mutates in place — Compose is **not** notified, so the UI goes stale | Recorded as a state write; readers recompose |
| Replacing the list | `state.value = newList` recomposes readers | Not needed — mutate in place |
| Use case | Immutable lists you replace wholesale (`state.value = state.value + item`) | Lists you mutate in place in the UI layer |

```kotlin
// ✅ Good: observable list — add/remove notifies readers
val selectedIds = remember { mutableStateListOf<String>() }

// ❌ Bad: in-place mutation of a plain list is invisible to Compose
val allItems by remember { mutableStateOf(mutableListOf<String>()) }
allItems.add("x") // no recomposition
```

### `LaunchedEffect` & `DisposableEffect` best practices

```kotlin
@Composable
fun SafeEffectExample(trigger: String) {
    // ✅ Safe: restarts when trigger changes; the coroutine is cancelled
    // when the key changes or the composable leaves composition
    LaunchedEffect(trigger) {
        // one‑off async work
        webSocket.send(trigger)
    }

    // ✅ Safe: runs once on entering composition; onDispose cancels the job on exit
    DisposableEffect(Unit) {
        val job = CoroutineScope(Dispatchers.IO).launch { /* … */ }
        onDispose { job.cancel() }
    }
}
```

- **Use `rememberUpdatedState`** for values (e.g. callbacks) a long‑running effect should always read at their latest, without restarting the effect; otherwise the effect keeps the value it captured when it launched.
- **Put all cleanup in `onDispose`** — `DisposableEffect` requires it — so listeners and coroutines don’t leak when the composable is removed from the hierarchy unexpectedly.

<Callout variant="note">
If you find yourself writing `LaunchedEffect(key1, key2, key3)` with more than two keys, consider pulling the logic into a ViewModel or a dedicated side‑effect composable — deep key lists are a code smell for “doing too much in UI composition.”
</Callout>

### Profiling recompositions

```bash
# 1. In Android Studio, open Layout Inspector on a running debug build and
#    enable "Show Recomposition Counts" to see recompositions and skips per composable.

# 2. Generate Compose compiler stability reports. In build.gradle.kts:
#      composeCompiler { reportsDestination = layout.buildDirectory.dir("compose_compiler") }
./gradlew assembleRelease

# Then inspect build/compose_compiler/*-composables.txt for functions
# that are "restartable" but not "skippable", and *-classes.txt for unstable classes.
```

A good rule of thumb: if a composable’s recomposition count keeps climbing while nothing it displays has changed, refactor state ownership or defer the state read (`derivedStateOf`, lambda‑based modifiers).
