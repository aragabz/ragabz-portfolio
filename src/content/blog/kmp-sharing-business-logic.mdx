The promise of Kotlin Multiplatform is one source of truth for your app's logic — here's how to make it work beyond a shared UI toolkit.

<Callout variant="tip" title="What you'll learn">
- How to set up a `commonMain` module with Koin for DI
- Writing a shared Ktor client that works on JVM, iOS, and WasmJS
- Serialization strategies: kotlinx.serialization in `commonMain` (and why Moshi stays JVM‑only)
</Callout>

### Multi‑module project layout

```text
my-app/
├── shared/
│   └── src/commonMain/  # Shared Kotlin code (models, DI, networking)
├── androidApp/          # Android UI (Compose) + MainActivity
├── iosApp/              # Xcode project consuming the shared framework
├── desktopApp/          # JVM desktop (optional)
└── webApp/              # WasmJS entry point
```

### Shared models & DI with Koin

```kotlin
// commonMain
import org.koin.core.module.dsl.viewModel
import org.koin.dsl.module

// Data models
@Serializable
data class User(val id: Int, val name: String, val email: String)

// Koin module
val commonModule = module {
    single { httpClient }
    single<UserApi> { KtorUserApi(get()) }
    single { UserRepository(get()) }
    viewModel { UserViewModel(get()) }
}

// UserViewModel (androidx.lifecycle ViewModel is multiplatform)
class UserViewModel(private val repo: UserRepository) : ViewModel() {
    private val _uiState = MutableStateFlow<UiState>(UiState.Loading)
    val uiState: StateFlow<UiState> = _uiState.asStateFlow()

    fun load() {
        viewModelScope.launch {
            _uiState.value = UiState.Success(repo.getUser())
        }
    }
}
```

Koin works across all targets because its DSL is plain Kotlin lambdas resolved at runtime — no reflection and no code‑gen step required.

### Shared Ktor client

```kotlin
// commonMain — Ktor setup
val httpClient: HttpClient = HttpClient {
    install(ContentNegotiation) {
        json(Json { ignoreUnknownKeys = true }) // kotlinx.serialization
    }
    defaultRequest {
        header(HttpHeaders.Accept, ContentType.Application.Json)
    }
}

// Add one engine per platform (ktor-client-okhttp in androidMain, ktor-client-darwin
// in iosMain, ktor-client-js in wasmJsMain); HttpClient {} picks it up automatically,
// so no expect/actual is needed for the client itself.
```

On iOS, add `ktor-client-darwin` to `iosMain` in the shared module’s `build.gradle.kts`; the Xcode project just links the shared framework, and the `commonMain` client works unchanged.

### Serialization per platform

```kotlin
// commonMain — one Json configuration shared by Ktor and local storage
val AppJson = Json {
    ignoreUnknownKeys = true   // tolerate new server fields
    explicitNulls = false
}

@Serializable
data class UserDto(
    val id: Int,
    @SerialName("full_name") val name: String,
    val email: String,
)
```

The kotlinx.serialization compiler plugin generates serializers at compile time for every target, so there’s no `expect/actual` and no reflection — the same `@Serializable` class works on JVM, iOS, and Wasm. Keep reflection‑based libraries like Moshi or Gson out of `commonMain`; they only run on the JVM.

<Callout variant="warning">
On iOS and web there is no reflection, so open polymorphic hierarchies (an `interface` or `abstract class` with subclasses in other modules) must be registered explicitly in a `SerializersModule`; otherwise deserialization fails at runtime with a `SerializationException`. Sealed hierarchies are handled by the plugin automatically.
</Callout>

### Testing the shared layer

```kotlin
// commonTest
class UserRepositoryTest {
    @Test fun loadUserFromRepoReturnsExpectedModel() = runTest {
        val repo = UserRepository(FakeUserApi(User(1, "Alice", "alice@test")))
        assertEquals(User(1, "Alice", "alice@test"), repo.getUser())
    }
}
```

Since the repo lives in `commonMain` and the test in `commonTest`, the same test suite runs on Android, iOS test targets, and CI pipelines — one source of truth for logic correctness.
