### Cancellation-aware `try / catch` blocks

```kotlin
suspend fun fetchUser(id: Int): User {
    return withContext(Dispatchers.IO) {
        try {
            // Simulate a network call that can be cancelled
            val result = repository.fetch(id)
            result.also { /* log success */ }
        } catch (e: CancellationException) {
            // 👇 Cancel‑aware: re‑throw CancellationException so cancellation
            // propagates instead of being swallowed
            throw e
        } catch (e: Exception) {
            // 👇 All other failures (network timeout, deserialization, etc.)
            logError("User fetch failed", e)
            throw e  // or return fallback; depends on your error policy
        }
    }
}
```

- **`CancellationException`** is the mechanism for cooperative cancellation; never swallow it — if you catch it (or a broad `Exception`/`Throwable`), re‑throw it.
- **`catch (e: Exception)`** catches everything else (IOExceptions, JSON errors). Decide per‑call whether to propagate or return a fallback.

### `SupervisorJob` vs. `CoroutineExceptionHandler`

| | `SupervisorJob` / `supervisorScope` | `CoroutineExceptionHandler` |
|-------|----------------------|----------------------------|
| What it does | A failing child does **not** cancel its parent or siblings | Last‑resort callback for an *uncaught* exception — it doesn't recover or prevent cancellation |
| Where it takes effect | The scope/job whose children should fail independently | Only in a root coroutine's context (the scope or a top‑level `launch`); ignored in nested children and by `async` |
| Typical use | `viewModelScope` and `lifecycleScope` (already supervisor‑based), app‑level scopes | Logging/crash reporting for top‑level `launch { }` |
| Example | `CoroutineScope(SupervisorJob() + Dispatchers.Main)` | `CoroutineExceptionHandler { _, throwable -> log(throwable) }` |

**Rule of thumb:** Use a `SupervisorJob` at the outermost scope (Application or ViewModel) so one failing coroutine doesn't cancel all its siblings. Add a `CoroutineExceptionHandler` to that root context for logging; for actual recovery, use `try / catch` inside the coroutine.

```kotlin
// ✅ Top‑level scope with supervisor + last‑resort handler
val appScope = CoroutineScope(
    SupervisorJob() + Dispatchers.Main +
        CoroutineExceptionHandler { _, throwable -> logError("Uncaught", throwable) }
)

// ✅ Recovery for THIS job happens inside it
appScope.launch {
    try {
        riskyOperation()
    } catch (e: CancellationException) {
        throw e
    } catch (e: Exception) {
        // handle/fallback; siblings in appScope are unaffected either way
    }
}
```

### `retryWhen` and `catch` for resilient pipelines

```kotlin
val userStream: Flow<UserUiState> = repository.userStream()
    .map<User, UserUiState> { UserUiState.Loaded(it) }
    .retryWhen { cause, attempt ->
        // Retry only on transient errors; give up after 3 retries
        cause is IOException && attempt < 3
    }
    .catch { exception ->
        val message = when (exception) {
            is IOException -> "Network error — tap to retry"
            is JsonSyntaxException -> "Data corruption — abort"
            else -> "Unexpected error — log and abort"
        }
        emit(UserUiState.Error(message))
    }
```

- `retryWhen` gives you control over *when* to retry (attempt count, exception type, back‑off logic).
- `catch` turns the error into a UI‑friendly state; the UI can decide to show a retry button or go to an error screen.

<Callout variant="note">
Don't wrap an existing `Flow` (e.g., a repository stream) in a new `flow { }` builder with `try / catch` around `collect` just to handle errors. Use `catch` as an operator on the existing flow instead — it preserves the original producer and only taps into error handling. Note that `catch` only sees **upstream** exceptions, not ones thrown inside your `collect { }`.
</Callout>

### Avoiding coroutine leaks

1. **Always tie coroutine scopes to a lifecycle owner:** `viewModelScope`, `lifecycleScope`, or an explicit `CoroutineScope(job)` that you cancel in `onCleared()` / `onDestroy()`.
2. **Never launch inside a `remember` block** unless the job is explicitly tied to the `remember` key's lifecycle.
3. **Use `withTimeout()` / `withTimeoutOrNull()`** for IO operations that might hang — `withTimeout` throws `TimeoutCancellationException`, `withTimeoutOrNull` returns `null` instead:
   ```kotlin
   val result = withTimeoutOrNull(5_000) { repository.fetch(id) }
   ```
4. **Avoid ad‑hoc `CoroutineScope(Dispatchers.Main).launch { }`** — nothing cancels that scope, so it leaks. Launch UI work from the lifecycle scope (`viewModelScope.launch { }`) and switch to `Dispatchers.IO` with `withContext` only around blocking calls.
