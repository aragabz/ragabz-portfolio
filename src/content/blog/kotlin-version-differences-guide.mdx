## The 1.x Era

Kotlin 1.0 shipped in February 2016; by 2.0 (May 2024) the language had grown enormously:

| Version | Year | Headline features |
|---------|------|-------------------|
| 1.0 | 2016 | First stable release |
| 1.1 | 2017 | Coroutines (experimental), type aliases, JS backend matured |
| 1.2 | 2017 | Multiplatform projects (experimental), array extensions in stdlib |
| 1.3 | 2018 | **Coroutines stable**, `when` on subjects without `var`, contracts API |
| 1.4 | 2020 | SAM conversions for Kotlin interfaces, trailing commas, IR-based JS backend preview |
| 1.5 | 2021 | Sealed interfaces, JVM records support, inline value classes stable, IR backend default for JS |
| 1.6–1.8 | 2022 | Stable exhaustive `when` over enums/sealed/Boolean, JVM target 18+, recursive generic generics cleanup |
| 1.9 | 2023 | **Data objects stable**, enum entries (`Direction.entries`), K2 compiler beta for all targets |

If you learned Kotlin before ~2020, coroutines were experimental and sealed hierarchies couldn't be interfaces — two things treated as bedrock in modern Kotlin.

## Why Rewrite the Compiler? K2 Explained

The original frontend ("K1") grew organically since 2010. Three problems compounded:

1. **Speed** — analysis ran multiple times across compilation phases; large builds spent minutes in the frontend alone.
2. **Divergence** — each target platform (JVM, JS, Native) had partially separate logic, so identical code could behave differently per target, and every new feature had to be implemented N times.
3. **Feature velocity** — adding anything to K1 risked destabilizing everything else. New language features were bottlenecked.

### What K2 actually changed

K2 is a new **frontend** built around FIR (Frontend Intermediate Representation):

- **One pipeline for all platforms** — resolution, typing, and diagnostics run once, then feed JVM/JS/Native/Wasm backends
- **~2× faster compilation** on large real-world projects
- **IDE sharing** — IntelliJ's code analysis runs the *same* engine as the compiler, so "works in IDE but fails to build" mismatches largely disappear

<Callout variant="note">
"Compiler rewrite" sounds scary, but your source code is untouched. Kotlin maintains strict binary and source compatibility guarantees — code that compiled on 1.9 compiles on 2.x with at most deprecation warnings.
</Callout>

### Smarter smart casts

The user-visible payoff you'll notice first. K2 casts more aggressively in cases K1 refused:

```kotlin
// 1) After logical OR type checks
fun process(obj: Any) {
    if (obj is String || obj is Int) {
        // K2 knows obj is Comparable<*> here;
        // K1 gave up and demanded explicit handling
    }
}

// 2) Variables captured before a lambda boundary
fun example(list: List<Int>) {
    var sum: Int? = null
    if (sum == null) return
    list.forEach { println(sum + it) }   // K2 smart-casts sum inside the lambda
}

// 3) Inline functions preserve null checks
inline fun <T> T.alsoIfNotNull(block: (T) -> Unit): T {
    if (this != null) block(this)
    return this as T
}

// 4) Exception variables
try { risky() } catch (e: Exception) {
    if (e !is IOException) throw e
    // e is smart-cast to IOException below in K2
}
```

Each case individually is small; together they delete a meaningful amount of `@Suppress` noise and redundant casts from real codebases.

### Compose compiler merged into Kotlin

From 2.0, the Jetpack Compose compiler plugin ships **as part of Kotlin itself** — one version number to manage instead of a matrix of Kotlin↔Compose-compiler pairings.

### Migration: 1.x → 2.0

For most projects this is a version-bump exercise, but do it deliberately:

```kotlin
plugins {
    id("org.jetbrains.kotlin.jvm") version "2.0.21"
}
```

1. **Update tooling first** — use an IDEA/Android Studio version bundled with K2-era plugins.
2. **Bump the plugin version**, build, and read warnings — deprecated APIs surface as warnings long before they break.
3. **Check kapt usage** — annotation processors like Dagger/Hibernate still work via kapt, but KSP is the supported path forward.
4. **Libraries**: confirm critical dependencies declare 2.0 support (Spring Boot 3.2+ and most kotlinx libraries were ready early).
5. **Language version pinning**: if your build pins `-language-version=1.9` during transition, new syntax stays unavailable even though the compiler is new. Remove pins once validated.

<Callout variant="warning">
K1 wasn't deleted immediately — 2.x releases kept it available behind flags through 2.1, with full removal announced for later versions. Don't rely on it: new features are K2-only forever.
</Callout>

### Compatibility philosophy

Worth internalizing because it explains the whole version story:

- **Binary compatibility** is sacred: a library compiled against Kotlin 1.0 links fine under 2.4
- **Source compatibility** is near-sacred: breaking changes arrive only via deprecation cycles spanning multiple releases
- **Experimental features opt-in explicitly** (`@OptIn`) and may change freely until stabilized

This is why teams can upgrade compilers eagerly and libraries conservatively — the ecosystem doesn't fragment the way some languages do.

## Kotlin 2.1–2.2: The Language Wave

K2 rebuilt the foundation; the 2.1 and 2.2 releases built the house. This was the richest wave of **syntax-level** additions since coroutines.

### Timeline at a glance

| Feature | 2.1 (Nov 2024) | 2.2 (Jun 2025) |
|---------|----------------|----------------|
| Guard conditions in `when` | Experimental | **Stable** |
| Non-local `break`/`continue` | Experimental | **Stable** |
| Multi-dollar interpolation | Experimental | **Stable** |
| Context parameters | — | Experimental |
| Nested type aliases | — | Beta |

Notice the pattern: announce experimentally, stabilize quickly after real-world feedback.

### Guard conditions in `when`

**Problem:** `when` matched *values*, but branch conditions combining two things forced nested checks or duplicated patterns.

```kotlin
// BEFORE — nesting to express "Success AND code 200"
when (result) {
    is Success -> if (result.code == 200) render(result.body)
                  else showWarning(result)
    is Error -> showError(result)
}
```

Guards attach `if` conditions directly to branches:

```kotlin
// AFTER (stable in 2.2)
when (result) {
    is Success if result.code == 200 -> render(result.body)
    is Success -> showWarning(result)
    is Error -> showError(result)
}
```

Evaluation order is top-down as usual, so guards compose naturally with sealed hierarchies:

```kotlin
when (user) {
    is Admin if user.isActive -> grantRoot()
    is Admin -> lockAccount(user)
    is Guest -> offerSignup()
}
```

Exhaustiveness checking still works — the compiler verifies every case remains reachable.

### Non-local `break` and `continue`

**Problem:** inside an inline lambda like `forEach`, you couldn't `break` the enclosing loop — only label-return hacks worked:

```kotlin
// BEFORE — the run-block trick or labeled returns
run outer@ {
    rows.forEach { row ->
        cells.forEach { cell ->
            if (!cell.isValid) return@outer   // exits everything, awkwardly
        }
    }
}
```

Now `break`/`continue` reach through inline lambdas to their enclosing loops:

```kotlin
// AFTER (stable in 2.2)
for (row in rows) {
    cells.forEach { cell ->
        if (!cell.isValid) break       // breaks the FOR loop itself
        if (cell.isSkipped) return@forEach
        total += cell.value
    }
}
```

Plain `break` targets the innermost *enclosing loop* even across the lambda boundary. Labels still work for outer loops (`break@rows`). This finally closes one of Java-lambda-migration's most common complaints.

### Multi-dollar string interpolation

**Problem:** generating shell scripts, JSON templates, or regex containing literal `$` required ugly escapes:

```kotlin
// BEFORE
val script = "echo \$HOME costs ${'$'}{amount}"     // 😬
```

Prefixing with extra dollars re-defines the interpolation marker:

```kotlin
// AFTER (stable in 2.2)
val amount = 42
val script = $$"echo $HOME costs $$amount"

println(script)   // echo $HOME costs 42
```

Rules: `$$"..."` treats single `$` as literal text; `$$x` performs interpolation. Need both literal `${'$$'}` sequences AND interpolation in one string? Go to `$$$`. Rarely needed — but when you need it, nothing else comes close.

### Context parameters (experimental, 2.2)

The successor to the deprecated *context receivers* proposal. They let functions receive implicit dependencies declared at call sites:

```kotlin
context(logger: Logger, clock: Clock)
suspend fun processOrder(order: Order): Receipt {
    logger.info("Processing ${order.id} at ${clock.now()}")
    return Receipt(order.id, clock.now())
}
```

Callers supply contexts explicitly at the boundary:

```kotlin
context(providedLogger, systemClock) {
    processOrder(order)
}
```

Why this matters: logging, clocks, random sources, and transaction handles are *ambient* dependencies today — usually solved by threading them manually or reaching for DI containers everywhere. Context parameters give library authors a middle path without magic globals.

<Callout variant="warning">
Context *receivers* (`context(Type)` without names) are deprecated — if you experimented with them in 1.6–1.9 era libraries, migrate to the named-parameter form.
</Callout>

### Nested type aliases (beta, 2.2)

Type aliases could only be top-level; now they nest inside classes:

```kotlin
class Inventory {
    typealias Sku = String                 // scoped to Inventory
    
    private val stock = mutableMapOf<Sku, Int>()
    fun add(sku: Sku, qty: Int = 1) { stock.merge(sku, qty, Int::plus) }
}
```

Referenced externally as `Inventory.Sku`. Small feature, real benefit: aliases live near what they describe instead of polluting package level.

### How features reach you safely

Every addition above followed the same pipeline — understanding it removes upgrade anxiety:

1. **Experimental**: requires explicit `@OptIn(ExperimentalXyz::class)` per file/module; behavior may change arbitrarily between releases
2. **Beta**: shape settled; still opt-in but migration paths guaranteed
3. **Stable**: on by default at the new language version; older `-language-version` pins keep old behavior during transition

```kotlin
kotlin {
    compilerOptions {
        optIn.add("kotlin.ExperimentalStdlibApi")
    }
}
```

Upgrading the *compiler* never silently injects unstable semantics into your source — stability arrives only when your `language-version` catches up.

### Migration: 2.0 → 2.2

Genuinely low-friction:

1. Bump plugin version; rebuild. The three 2.2-stabilized features activate automatically because they were additive syntax.
2. Search for `@OptIn(ExperimentalStdlibApi` and similar markers — many can simply be deleted once you're on the matching language version.
3. Replace any context-receiver usage (compiler will warn).
4. Watch for stricter diagnostics — K2-era releases tightened some resolution rules.

## Kotlin 2.3–2.4: The Stabilization Era

After the K2 rewrite and the language wave, Kotlin entered a **stabilization era**: fewer flashy additions, more graduation of experiments into everyday tools, plus serious multiplatform polish.

### How Kotlin releases work now

Two independent tracks since 2023:

- **Language releases** (`2.3.0`, `2.4.0`) every ~6 months — may add/stabilize language features
- **Tooling releases** (`2.3.20`, `2.4.10`) between them — bugfixes, platform support, tooling; **never** change language semantics

Practical consequence: you can adopt `X.Y.20` maintenance releases fearlessly mid-quarter, while planning `X.(Y+1).0` upgrades deliberately.

### Kotlin 2.3 (December 2025)

#### Stabilized: nested type aliases & smarter `when` exhaustiveness

**Data-flow-based exhaustiveness checking** for `when` became stable — the compiler now understands guards and complex conditions when deciding whether your `when` covers all cases:

```kotlin
sealed interface Event {
    data class Click(val x: Int, val y: Int) : Event
    data object Refresh : Event
}

fun handle(e: Event) = when (e) {
    is Click if e.x >= 0 -> move(e)
    is Click -> clamp(e)          // compiler PROVES remaining clicks land here
    Refresh -> reload()
}                                  // exhaustive — no else required
```

#### Enabled by default: explicit backing fields

Properties can now declare their storage explicitly — including a backing field of a *different type* than the exposed property:

```kotlin
import java.util.UUID

class Order {
    val id: String
        field: UUID = UUID.randomUUID()   // stores a UUID…
        get() = field.toString()           // …exposes a String
}
```

Before this, the workaround was a second private property (`private val _id`), doubling naming noise across millions of lines of Kotlin. The `field` keyword finally owns first-class storage.

#### Experimental: unused return value checker

A whole category of bugs — calling a function and silently discarding its result — becomes visible:

```kotlin
val errors = mutableListOf<String>()

errors.add("missing id")    // ⚠️ warning: return value unused
                            // add() returns Boolean — did you mean contains()?
val added = errors.add("x") // ✅ explicit
```

It's driven by annotations (stdlib functions like `add`, `checkNotNull`, builders are annotated) and rolls out gradually.

#### Standard library: time and identity

- **`kotlin.time.Clock` and `Instant`** stabilized — portable time tracking across platforms, ending the need for kotlinx-datetime shims in shared code
- **UUID API improved** (generation/parsing), later stabilized in 2.4

#### Platform highlights

| Area | Change |
|------|--------|
| JVM | Java 25 bytecode support |
| Kotlin/Native | Up to **40% faster release builds**, C/Obj-C import reaches Beta |
| Swift export | Enums export as native Swift enums; variadic function support |
| Kotlin/Wasm | New exception-handling proposal on by default |

#### The breaking-changes corner

`-language-version=1.8` support ended (and 1.9 became JVM-only), the ancient `kotlin-android-extensions` plugin now hard-fails configuration, and Ant build support was removed.

### Kotlin 2.3.20 (March 2026)

A tooling release with one big preview: **name-based destructuring**. Positional destructuring has always had a footgun:

```kotlin
data class Money(val amount: Long, val currency: String)

val price = Money(amount = 99, currency = "EUR")
val (amount, currency) = price        // positional — order matters!

val (currency2, amount2) = price      // compiles fine. Silently swapped. 💥
```

Name-based destructuring binds components **by property name**, so reordering a data class can never silently corrupt call sites:

```kotlin
// experimental preview (2.3.20+) — syntax still evolving before stabilization
val [amount = amt, currency = cur] = price
// amt ← price.amount, cur ← price.currency — regardless of declaration order
```

Same release refined overload resolution for context parameters and simplified Maven project setup.

### Kotlin 2.4 (June 2026)

The headline: **context parameters and explicit backing fields are stable**. Two of the most-requested ergonomic features are now production-grade:

```kotlin
// Ambient dependencies without DI-framework ceremony — now guaranteed-stable:
context(clock: Clock, logger: Logger)
fun audit(event: String) {
    logger.log("${clock.now()} :: $event")
}
```

Also in 2.4:

| Area | Highlights |
|------|-----------|
| Stdlib | **UUID API stable**; sorted-order checks (`isSorted*`) |
| JVM | Java 26 support; annotations preserved in metadata by default |
| Kotlin/Native | **Swift packages as dependencies**; CMS garbage collector on by default |
| Kotlin/Wasm | Incremental compilation by default; WebAssembly **Component Model** support |
| Kotlin/JS | Value classes exportable; ES2015-level output |
| Build | Gradle 9.5 compatibility; Maven auto-aligns Java↔JVM targets |

The multiplatform story is quietly becoming the main event: Swift package integration and the Wasm Component Model position Kotlin as a first-class citizen beyond Android and server.

## Migration Guidance

For a typical JVM/backend project on 2.0–2.2 moving to 2.4.x:

1. **Bump the plugin version**, rebuild, triage warnings first — deprecations removed in 2.3 will announce themselves loudly.
2. **Delete obsolete workarounds**: `_field` companion properties → explicit backing fields; manual parameter threading → consider context parameters where it genuinely simplifies.
3. **Enable the unused-return checker** in CI before turning it on locally — cheap early wins.
4. **Android projects**: verify AGP compatibility matrix alongside; Compose compiler ships with Kotlin now, so one version bump covers both.
5. **Libraries**: compile against the *lowest* language version you promise to support; consumers on older compilers stay compatible thanks to binary-compatibility guarantees.
