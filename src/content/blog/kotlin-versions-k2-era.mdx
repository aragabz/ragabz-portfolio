## The 1.x Era in One Table

Kotlin 1.0 shipped in February 2016; by 2.0 (May 2024) the language had grown enormously:

| Version | Year | Headline features |
|---------|------|-------------------|
| 1.0 | 2016 | First stable release |
| 1.1 | 2017 | Coroutines (experimental), type aliases, JS backend matured |
| 1.2 | 2017 | Multiplatform projects (experimental), array extensions in stdlib |
| 1.3 | 2018 | **Coroutines stable**, `when` on subjects without `var`, contracts API |
| 1.4 | 2020 | SAM conversions for Kotlin interfaces, trailing commas, IR-based JS backend preview |
| 1.5 | 2021 | Sealed interfaces, JVM records support, inline value classes stable, IR backend default for JS |
| 1.6–1.8 | 2022 | Stable exhaustive `when` over enums/sealed/Boolean, JVM target 18+, recursive generic generics cleanup |
| 1.9 | 2023 | **Data objects stable**, enum entries (`Direction.entries`), K2 compiler beta for all targets |

If you learned Kotlin before ~2020, coroutines were experimental and sealed hierarchies couldn't be interfaces — two things this series treated as bedrock ([post #7](/blog/kotlin-series-07-coroutines), [post #5](/blog/kotlin-series-05-oop-data-classes)).

## Why Rewrite a Working Compiler?

The original frontend ("K1") grew organically since 2010. Three problems compounded:

1. **Speed** — analysis ran multiple times across compilation phases; large builds spent minutes in the frontend alone.
2. **Divergence** — each target platform (JVM, JS, Native) had partially separate logic, so identical code could behave differently per target, and every new feature had to be implemented N times.
3. **Feature velocity** — adding anything to K1 risked destabilizing everything else. New language features were bottlenecked.

## K2: What Actually Changed

K2 is a new **frontend** built around FIR (Frontend Intermediate Representation). Key properties:

- **One pipeline for all platforms** — resolution, typing, and diagnostics run once, then feed JVM/JS/Native/Wasm backends
- **~2× faster compilation** on large real-world projects (JetBrains measured their own builds; results vary)
- **IDE sharing** — IntelliJ's code analysis runs the *same* engine as the compiler, so "works in IDE but fails to build" mismatches largely disappear

<Callout variant="note">
"Compiler rewrite" sounds scary, but your source code is untouched. Kotlin maintains strict binary and source compatibility guarantees — code that compiled on 1.9 compiles on 2.x with at most deprecation warnings.
</Callout>

### Smarter Smart Casts

The user-visible payoff you'll notice first. K2 casts more aggressively in cases K1 refused:

```kotlin
// 1) After logical OR type checks
fun process(obj: Any) {
    if (obj is String || obj is Int) {
        // K2 knows obj is Comparable<*> here;
        // K1 gave up and demanded explicit handling
    }
}

// 2) Variables captured before a lambda boundary
fun example(list: List<Int>) {
    var sum: Int? = null
    if (sum == null) return
    list.forEach { println(sum + it) }   // K2 smart-casts sum inside the lambda
}

// 3) Inline functions preserve null checks
inline fun <T> T.alsoIfNotNull(block: (T) -> Unit): T {
    if (this != null) block(this)        // caller gets smart cast after the call site
    return this as T
}

// 4) Exception variables
try { risky() } catch (e: Exception) {
    if (e !is IOException) throw e
    // e is smart-cast to IOException below in K2
}
```

Each case individually is small; together they delete a meaningful amount of `@Suppress` noise and redundant casts from real codebases.

### Compose Compiler Merged Into Kotlin

From 2.0, the Jetpack Compose compiler plugin ships **as part of Kotlin itself** — one version number to manage instead of a matrix of Kotlin↔Compose-compiler pairings. Android release notes now say "upgrade Kotlin" rather than "upgrade the Compose compiler".

## Migration Checklist: 1.x → 2.0

For most projects this is a version-bump exercise, but do it deliberately:

```kotlin
plugins {
    id("org.jetbrains.kotlin.jvm") version "2.0.21"
}
```

1. **Update tooling first** — use an IDEA/Android Studio version bundled with K2-era plugins; older IDEs can't analyze 2.0 output.
2. **Bump the plugin version**, build, and read warnings — deprecated APIs surface as warnings long before they break.
3. **Check kapt usage** — annotation processors like Dagger/Hibernate still work via kapt, but KSP is the supported path forward; plan the switch separately (it typically yields big build-speed wins).
4. **Libraries**: confirm critical dependencies declare 2.0 support (Spring Boot 3.2+ and most kotlinx libraries were ready early).
5. **Language version pinning**: if your build pins `-language-version=1.9` during transition, new syntax stays unavailable even though the compiler is new. Remove pins once validated.

<Callout variant="warning">
K1 wasn't deleted immediately — 2.x releases kept it available behind flags through 2.1, with full removal announced for later versions (IntelliJ deprecated K1 mode entirely during 2025). Don't rely on it: new features are K2-only forever.
</Callout>

## Compatibility Philosophy

Worth internalizing because it explains the whole series:

- **Binary compatibility** is sacred: a library compiled against Kotlin 1.0 links fine under 2.4
- **Source compatibility** is near-sacred: breaking changes arrive only via deprecation cycles spanning multiple releases
- **Experimental features opt-in explicitly** (`@OptIn`) and may change freely until stabilized

This is why teams can upgrade compilers eagerly and libraries conservatively — the ecosystem doesn't fragment the way some languages do.
