A solid offline‑first layer lets your app work when the network disappears and keeps the UI predictably reactive.

<Callout variant="tip" title="What you'll learn">
- How to write Room entities with proper `@PrimaryKey` and `@ColumnInfo`
- Exposing data as `Flow` vs. `LiveData` and when to choose each
- Patterns for repository‑scoped coroutine scopes and `viewModelScope`
</Callout>

### Room entities & DAOs

```kotlin
@Entity(tableName = "users")
data class User(
    @PrimaryKey @ColumnInfo(name = "user_id") val id: Int,
    @ColumnInfo(name = "name") val name: String,
    @ColumnInfo(name = "email") val email: String
)

@Dao
interface UserDao {
    @Insert(onConflict = OnConflictStrategy.IGNORE)
    suspend fun insert(user: User)

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertAll(users: List<User>)

    @Query("SELECT * FROM users WHERE user_id = :id")
    suspend fun getById(id: Int): User?

    @Query("SELECT * FROM users")
    fun loadAll(): Flow<List<User>>
}
```

`suspend` functions handle one‑shot reads and writes; a `Flow` return type gives a cold observable stream — Room re‑runs the query and emits whenever the `users` table changes, and only does that work while something is collecting.

### Repository layer with Flow

```kotlin
class UserRepository(private val dao: UserDao, private val api: UserApi) {
    // Room is the single source of truth: the UI only ever observes the database
    val users: Flow<List<User>> = dao.loadAll()
        .distinctUntilChanged()

    // Network results are written into Room, which re-emits to every collector
    suspend fun refresh() {
        val remote = api.fetchUsers()
        dao.insertAll(remote)
    }
}
```

Reading only from Room keeps the cached data on screen while the network call is in flight (or failing offline); when `refresh()` writes new rows, Room re‑emits, and `distinctUntilChanged` drops emissions where the list hasn't actually changed — Room re‑queries on *any* write to the table.

<Callout variant="warning">
Avoid exposing `LiveData` from a Repository — it’s an Android UI‑layer type that delivers on the main thread and lacks Flow’s operators. Expose `Flow`, and collect it in Compose with `collectAsStateWithLifecycle()` (or `repeatOnLifecycle { flow.collect { ... } }` in Views). If a View‑based screen still needs `LiveData`, convert at the ViewModel with `flow.asLiveData()`.
</Callout>

### UI consumption

```kotlin
class UserViewModel(private val repository: UserRepository) : ViewModel() {
    val users: StateFlow<List<User>> = repository.users
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), emptyList())

    fun refresh() {
        viewModelScope.launch { repository.refresh() }
    }
}

@Composable
fun UserScreen(viewModel: UserViewModel) {
    val users by viewModel.users.collectAsStateWithLifecycle()

    Column {
        Button(onClick = viewModel::refresh) {
            Text("Refresh")
        }
        LazyColumn {
            if (users.isEmpty()) {
                item { Text("No users — tap Refresh", style = MaterialTheme.typography.bodyMedium) }
            }
            items(users, key = { it.id }) { user ->
                UserCard(user)
            }
        }
    }
}
```

`stateIn(viewModelScope, …)` turns the repository `Flow` into a `StateFlow` owned by the ViewModel, so it survives configuration changes, and `collectAsStateWithLifecycle()` stops collecting while the UI is in the background — no leaked collectors.
