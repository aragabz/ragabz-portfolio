When building large-scale React applications, proper architecture and organization become critical for maintainability and performance.

<Callout variant="tip" title="The three rules of scale">
1. **Structure by feature**, not by file type.
2. **Own your data flow** — pick a state strategy and stick to it.
3. **Ship less JavaScript** — split code at the route boundary.
</Callout>

## Key Principles

1. **Component Organization**: Keep components small and focused
2. **State Management**: Choose the right tool for your needs
3. **Code Splitting**: Lazy load components and routes
4. **Type Safety**: Use TypeScript for better DX

## State Management Strategy

For large applications, consider a combination of approaches rather than a single library.

### React Context for shared UI state

Context is perfect for low-frequency, cross-cutting state like theme or auth:

```typescript
// context/ThemeContext.tsx
export const ThemeContext = createContext<Theme>('light');

export function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [theme, setTheme] = useState<Theme>('light');

  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      {children}
    </ThemeContext.Provider>
  );
}
```

<Callout variant="warning">
Avoid putting rapidly-changing state in Context — every update re-renders every consumer. For high-frequency updates, reach for a state library or local state instead.
</Callout>

### Global state: Zustand or Redux Toolkit

For state shared across many parts of the app:

```typescript
// Example using Zustand
import create from 'zustand';

interface AppState {
  user: User | null;
  setUser: (user: User) => void;
}

export const useStore = create<AppState>((set) => ({
  user: null,
  setUser: (user) => set({ user }),
}));
```

### Server state: React Query

Server data deserves its own layer — caching, retries, and invalidation handled for you:

```typescript
import { useQuery } from '@tanstack/react-query';

function Profile() {
  const { data, isLoading } = useQuery({
    queryKey: ['user'],
    queryFn: () => fetchUser(),
  });

  return isLoading ? <Spinner /> : <UserCard user={data} />;
}
```

<Callout variant="note" title="Rule of thumb">
Context for UI state, React Query for server state, Zustand/Redux for complex client-side global state. Fewer tools, clearer boundaries.
</Callout>

## Performance Optimization

Always measure before optimizing. Use React DevTools Profiler to identify bottlenecks.

### Memoization with useMemo and useCallback

Don't over-optimize — profile first, then memoize only what is actually re-rendering.

### Code splitting with React.lazy

```typescript
const Dashboard = lazy(() => import('./Dashboard'));

function App() {
  return (
    <Suspense fallback={<Loading />}>
      <Dashboard />
    </Suspense>
  );
}
```

### Virtual scrolling for long lists

Libraries like `@tanstack/react-virtual` render only the visible rows — a must for feeds, tables, and logs.

### Image optimization and lazy loading

- Use `next/image` or `astro:assets` for automatic optimization
- Set explicit dimensions to prevent layout shift
- Lazy-load below-the-fold images with `loading="lazy"`

## Key Takeaways

- Organize by **feature** — each feature owns its components, hooks, and types
- Split state by **concern**: Context / server state / global state
- **Measure before optimizing**; start with the biggest re-renders
- Make code splitting a **default**, not an afterthought

<Callout variant="tip" title="Progressive migration">
You don't need to refactor everything at once. Adopt these patterns feature-by-feature; each one reduces complexity independently.
</Callout>

## Conclusion

Building scalable React apps requires thoughtful architecture, proper tooling, and continuous optimization.
