Compose has its own state model, and knowing which tool fits which problem saves hours of debugging.

<Callout variant="tip" title="What you'll learn">
- When `remember { mutableStateOf() }` is enough vs. when you need `derivedStateOf`
- How to structure a simple MVI loop with `StateFlow` and `collectAsStateWithLifecycle`
- Why reaching for a global Redux-style store often adds unnecessary ceremony
</Callout>

## Compose‑first state

```kotlin
@Composable
fun Counter() {
    // UI‑only state: survives recomposition (use rememberSaveable to survive config changes)
    var count by remember { mutableStateOf(0) }
    // Derived state: readers only recompose when the *result* flips
    val isOverLimit by remember { derivedStateOf { count > 10 } }

    Button(onClick = { count++ }, enabled = !isOverLimit) {
        Text(text = if (isOverLimit) "Limit reached" else "Add")
    }
}
```

`remember { mutableStateOf() }` triggers a recomposition of its readers whenever the value changes (compared with structural equality by default). `derivedStateOf` only notifies readers when its computed result changes — use it when the input changes far more often than the output (scroll position → “show the FAB?”). For an expensive calculation that just depends on parameters, `remember(key) { … }` is the right tool.

## When global stores make sense

| Situation | Recommended tool |
|-----------|-----------------|
| Shared auth token across many distant screens | `AuthRepository` + `ViewModel` + `Hilt` |
| Complex form validation with cross‑field rules | A screen‑level `ViewModel` exposing one `StateFlow<FormState>` |
| Time‑travel debugging or action logging | A Redux‑style store (e.g. ReduxKotlin) with reducers and middleware |

<Callout variant="warning">
Avoid putting UI‑only data (e.g. animation progress, transient selections) into a global store — it forces every subscriber to re‑render on *any* store change, destroying Compose’s selective-subscription benefit.
</Callout>

## Simple MVI loop

```kotlin
// UI
@Composable
fun MyScreen(viewModel: MyViewModel) {
    val title by viewModel.title.collectAsStateWithLifecycle()
    Column {
        Text(title)
        Button(onClick = { viewModel.onIntent(MyIntent.LoadData) }) { Text("Load") }
    }
}

// Domain
sealed interface MyIntent {
    data object LoadData : MyIntent
}

class MyViewModel(private val repository: Repository) : ViewModel() {
    private val _title = MutableStateFlow("Hello")
    val title: StateFlow<String> = _title
        .map { "Updated: $it" }
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5000),
            initialValue = "Hello",
        )

    fun onIntent(intent: MyIntent) {
        when (intent) {
            MyIntent.LoadData -> viewModelScope.launch {
                _title.value = repository.fetch()
            }
        }
    }
}
```

Because `stateIn` runs in `viewModelScope`, the resulting `StateFlow` lives as long as the ViewModel — which survives configuration changes — and `WhileSubscribed(5000)` stops the upstream shortly after the UI stops collecting.

## When to reach for a global Redux‑style store

- **Cross‑screen workflows** (e.g. a multi‑step checkout) where several screens read and write the same state.
- **Time‑travel debugging** where you need exact action replay.
- **State that truly is global** (e.g. theme preferences stored in DataStore) and accessed from many unrelated screens.

**Bottom line:** Start with Compose’s `mutableStateOf` and coroutines’ `StateFlow`/`flow {}`. Only pull in a global store when the pattern above doesn’t fit your problem shape.
