A solid test suite gives you confidence to refactor Compose UIs without fear of breaking visual behavior.

<Callout variant="tip" title="What you'll learn">
- How to create and configure `createComposeRule`
- Testing `SideEffect`s and `remember`ed state in isolation
- Pixel‑diff regression testing with Roborazzi
</Callout>

### Basic compose test rule

```kotlin
@get:Rule
val composeTestRule = createComposeRule()

@Test fun `greeter composable shows entered name`() {
    composeTestRule.setContent {
        Greeting("Android")
    }

    // Find the node by its text via semantics and assert on it
    composeTestRule.onNodeWithText("Android").assertIsDisplayed()
}
```

`composeTestRule` drives a test clock (`mainClock`) and, by default, waits for the UI to be idle before every finder and assertion, so recompositions and animations settle predictably inside `@Test`. Set `composeTestRule.mainClock.autoAdvance = false` to step through time manually.

### Testing `SideEffect` and `remember`

```kotlin
@Test fun `remembered counter survives recomposition and side effect reports it`() {
    val reported = mutableListOf<Int>()

    composeTestRule.setContent {
        var count by remember { mutableStateOf(0) }
        val label = "Count: $count"           // read here so this scope recomposes
        SideEffect { reported += count }       // runs after every successful composition
        Button(onClick = { count++ }) { Text(label) }
    }

    // Act: click through the semantics tree
    composeTestRule.onNodeWithText("Count: 0").performClick()

    // Assert: state was kept and the side effect saw both compositions
    composeTestRule.onNodeWithText("Count: 1").assertIsDisplayed()
    assertEquals(listOf(0, 1), reported)
}
```

The rule creates a fresh composition for every test and disposes it afterwards, so `remember`‑based state never leaks between tests.

<Callout variant="warning">
Never call `setContent` twice in one test — the rule throws an `IllegalStateException`. To exercise a state change, drive it through the UI (clicks, text input) or through hoisted state you pass in, and let the rule handle teardown on test completion.
</Callout>

### Pixel‑diff regression with Roborazzi

```kotlin
@RunWith(AndroidJUnit4::class)
@GraphicsMode(GraphicsMode.Mode.NATIVE)
class HomeScreenScreenshotTest {
    @get:Rule
    val composeTestRule = createComposeRule()

    @Test fun `ui regression: home screen snapshot matches baseline`() {
        composeTestRule.setContent {
            HomeScreen() // your root composable
        }

        // Record with ./gradlew recordRoborazziDebug, compare with verifyRoborazziDebug
        composeTestRule.onRoot().captureRoboImage(
            roborazziOptions = RoborazziOptions(
                compareOptions = RoborazziOptions.CompareOptions(
                    changeThreshold = 0.01f, // 1 % pixel diff allowed
                ),
            ),
        )
    }
}
```

Roborazzi runs on the JVM with Robolectric, so screenshot tests are plain local unit tests — no emulator needed.

- Store baselines version‑controlled (e.g. point `roborazzi { outputDir }` at `src/test/screenshots/`) alongside the test.
- Run `./gradlew verifyRoborazziDebug` in CI as a `fail-fast` step — any visual change (intentional or not) will block the merge until the baseline is re‑recorded.
- Adjust `changeThreshold` per‑screen: tighter on exact‑layout screens (forms), looser on decorative or animated screens.

### Common testing pitfalls

| Pitfall | Fix |
|---------|-----|
| Coroutines launched with `GlobalScope` leak across tests | Use `rememberCoroutineScope()` or `LaunchedEffect` — they’re cancelled when the rule disposes the composition |
| Test order dependence (state leakage) | Keep state in composables or injected fakes, never in shared singletons; the rule gives each test a fresh composition |
| Pixel diff flakes on animated UIs | Set `mainClock.autoAdvance = false` and capture at a fixed frame, raise `changeThreshold`, or capture only static nodes instead of `onRoot()` |
